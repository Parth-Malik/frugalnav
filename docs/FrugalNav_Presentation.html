Knowing when to look.

An uncertainty-scheduled visual navigator for GPS-denied drones. Accurate enough to fly blind, frugal enough to run on an ultra-low-power RISC-V chip.

B.Tech independent project Parth Malik ROS 2 · Gazebo · portable C++ core

01 / The problem

When the GPS drops, the drone goes blind.

Indoors, deep in a canyon, or under jamming, a drone can't trust GPS. It falls back on dead-reckoning, adding up its own motion step by step. But every measurement has a small error, and those errors compound. Within seconds the drone's idea of where it is has drifted metres away from where it actually is.

Left uncorrected, it flies confidently into the wrong place.

02 / The catch

But fixing that drift is expensive.

To correct itself, the drone finds a known landmark and solves its geometry to recover an absolute position. It's accurate, and it's heavy on the processor. That leaves two bad options:

EVERY FRAME Constant correction drains a tiny drone's compute and battery.
FIXED TIMER Correcting on a clock lets drift explode between ticks.

03 / The question

What if it corrected only when it actually needed to?

Almost every system corrects on a fixed schedule, blind to whether the estimate is perfectly fine or falling apart. That either wastes power or risks the mission.

We wanted the drone to decide for itself, noticing the moment its own estimate is about to fail and paying for a fix only then.

04 / Our solution

Uncertainty-scheduled correction.

Track one live confidence number called U. It captures how much the drone should distrust its own position right now. Coast on cheap motion sensing while U is low. Spend an expensive landmark fix only when U crosses a threshold, the moment just before the estimate would break.

Correct when it matters. Save power the rest of the time.the core idea of the project

05 / The decider

How the drone senses it's about to get lost.

U blends live cues the drone already measures (its own position uncertainty, image sharpness, how many visual features it's losing, and sensor bias) into a single score from 0 to 1.

U = w₁·σ_pos + w₂·blur + w₃·feature-loss + w₄·bias  ∈ [0, 1]
  • Hard floor: force a fix before uncertainty gets dangerous, whatever the weights say.
  • Soft trigger: otherwise fire only when U > τ, catching trouble early from leading cues like a blurring image.
  • Cool-down: after a fix, wait a few ticks so it doesn't over-correct.

06 / The system

One estimate, many senses.

VIO gives cheap motion; ArUco markers give absolute fixes; a Kalman filter fuses them into one state the controller flies on; the laser dodges obstacles reactively. The scheduler sits on the fix line, the valve that makes the whole thing frugal.

07 / Why it's frugal

Cheap by construction.

  • The decision, computing U and comparing it to a threshold, is a handful of arithmetic operations. Trivial for a low-power RISC-V core.
  • The heavy vision work runs only when the scheduler asks for it. As we'll show, that's about half as often as a fixed timer.
  • The core is portable C++ with no operating system and no memory allocation in the hot loop, so it drops onto a microcontroller-class chip.

In our evaluation the scheduler matched a fixed-period baseline's accuracy while spending about half the landmark fixes, which is the result the whole project is built to demonstrate.

10 / It navigates

Reaches the goal on vision alone.

On dense-landmark worlds the drone flies start → target with no GPS and no map, correcting itself only when the scheduler fires.

  • Settles within about 1 metre of the target on the city and canyon courses.
  • The laser weaves it around obstacles, holding real clearance the whole way.
  • It drops altitude on its own when haze washes the ground out, then climbs back.
  • The ArUco fixes land within a few centimetres, from real pose-solving rather than a peek at ground truth.

11 / Toward real hardware

Sim today, PX4 tomorrow, same code.

A platform-adapter seam lets the identical navigator drive either the simulator or a real PX4 flight controller. Only the thin output layer changes; the scheduler, fusion and control are byte-for-byte the same.

We verified the PX4 offboard interface against the real message API. Arm, mode switch, and the 20 Hz setpoint stream all check out. Status, stated honestly: simulation-validated, not yet flight-tested.

12 / Honest limits & what's next

What it can't do yet.

  • Reactive avoidance can get trapped in tight or sparse obstacle fields. A lookahead planner (DWA, already prototyped) fixes this.
  • The motion sensor is a lightweight optical-flow proxy, not a full visual-inertial front-end.
  • Sensor calibration currently leans on simulator truth, so real hardware needs a one-time bench calibration.
  • It has not flown on a physical drone.

Next: a stronger estimator + global planner, a surveyed real-world landmark map, and a tethered first flight.

Frugal by design.
